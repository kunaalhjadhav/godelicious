# Godelicious — Setup Guide

A three-part food catering platform:

| Part | Stack | Purpose |
|---|---|---|
| `backend/` | Node.js + Express + Prisma | Single API used by the app, the web storefront, and the dashboard |
| `admin-dashboard/` | Next.js (port 3000) | Orders, menu, inventory, venue-enquiry review for admins/staff |
| `customer-app/` | React Native | Mobile ordering app + venue enquiry form |
| `customer-web/` | Next.js (port 3001) | Web storefront — same features as the mobile app, browser-based |

All four talk to **one backend**, so an order placed on web, mobile, or in-person appears instantly for staff in the dashboard, and stock/menu changes made in the dashboard show up on both the app and the website on next refresh.

> **Deploying to Railway or Render?** See `DEPLOYMENT_GUIDE.md` — this guide below covers local
> development only.

---

## 1. Backend setup (do this first — everything else depends on it)

```bash
cd backend
npm install
cp .env.example .env
npx prisma generate
npx prisma migrate dev --name init
npm run seed
npm run dev
```

This starts the API at `http://localhost:5000` using **SQLite** (a local file, `dev.db` — zero setup, perfect for development). The seed script creates test logins:

| Role | Email | Password |
|---|---|---|
| Admin | admin@godelicious.com | Admin@123 |
| Staff | staff@godelicious.com | Staff@123 |
| Customer | customer@godelicious.com | Customer@123 |

Verify it's running: open `http://localhost:5000/health` — you should see `{"status":"ok",...}`.

### Switching to PostgreSQL for production

1. In `prisma/schema.prisma`, change `provider = "sqlite"` to `provider = "postgresql"`.
2. In `.env`, set `DATABASE_URL` to your Postgres connection string (Railway, Render, Supabase, RDS, etc. all work).
3. Run `npx prisma migrate dev --name init` again against the new database.

## 2. Admin dashboard setup

```bash
cd admin-dashboard
npm install
cp .env.local.example .env.local
npm run dev
```

Open `http://localhost:3000` → sign in with the admin seed login above. `NEXT_PUBLIC_API_URL` in `.env.local` must point at your backend (defaults to `http://localhost:5000`, correct for local dev).

**Staff accounts:** the admin can create STAFF and additional ADMIN accounts via the `/api/users` endpoint (there's no UI page for this yet in the MVP — see "What to build next" below). For now, use a REST client (Postman/Insomnia) or `curl`:

```bash
curl -X POST http://localhost:5000/api/users \
  -H "Authorization: Bearer <admin_token>" \
  -H "Content-Type: application/json" \
  -d '{"name":"Kitchen Staff 2","email":"staff2@godelicious.com","password":"Staff@123","role":"STAFF"}'
```

Get `<admin_token>` from the response of `POST /api/auth/login`.

## 3. Customer web app setup

This is a browser-based counterpart to the mobile app — same menu browsing, cart, checkout, order tracking, and venue enquiry flow, sharing the same backend and the same brand identity, in a storefront layout (top nav + hero) rather than the dashboard's sidebar-ops layout.

```bash
cd customer-web
npm install
cp .env.local.example .env.local
npm run dev
```

Runs at `http://localhost:3001` (deliberately a different port from the admin dashboard's 3000, so you can run both at once locally). Sign in with the seed customer login:

```
customer@godelicious.com / Customer@123
```

Or register a new account directly from the site — both the web app and the mobile app create accounts through the same `/api/auth/register` endpoint, so a customer can sign in with the same credentials on either.

**Cart persistence:** the web cart is saved to the browser's `localStorage`, so it survives a page refresh (but is separate from the mobile app's cart — they're independent devices/sessions, same as any real e-commerce site).

## 4. Customer app (mobile) setup

The customer app is a **complete, standalone** React Native project — `customer-app/` contains
every screen, the navigation, cart/auth state, and the API client, fully wired to your backend.

It's missing only the native `android`/`ios` folders (Gradle files, `MainActivity`, app icons,
etc.), because those have to be generated by the React Native CLI on your machine — that step
downloads platform templates and binaries that need network access and your local Android SDK,
which isn't available in the environment these files were written in.

**Full step-by-step instructions — from scaffolding the native project through to a signed,
installable release APK — are in `customer-app/APK_BUILD_GUIDE.md`.** That covers:

1. Scaffolding the native Android/iOS project with the RN CLI
2. Dropping in the app code from this repo
3. Installing dependencies and pointing it at your backend
4. Testing a debug build end-to-end
5. Generating a release keystore and signing config
6. Building the actual release `.apk` (and `.aab` for Play Store submission)

Start there for the mobile app. The quick version, if you just want to test on an emulator
during development:

```bash
npx react-native@0.75.4 init GodeliciousApp --version 0.75.4
# then copy customer-app/App.js, customer-app/app.json, customer-app/index.js,
# and customer-app/src/ into the new GodeliciousApp/ folder (see APK_BUILD_GUIDE.md Step 2)
cd GodeliciousApp
npm install @react-native-async-storage/async-storage @react-navigation/native @react-navigation/native-stack @react-navigation/bottom-tabs react-native-safe-area-context react-native-screens
npx react-native run-android
```

## 5. How the "venue enquiry" flow works end-to-end

1. **Customer app or web:** "Enquire for a venue" → fills in venue name, location, date, guest count, budget, phone, notes → submits. (Identical form and flow on both platforms — same API call.)
2. **Backend:** stores it as `PENDING` on the `VenueEnquiry` table, tied to that customer's account.
3. **Admin dashboard:** Venue Enquiries page shows all pending enquiries → admin adds an optional note → clicks **Approve** or **Reject**.
4. **Customer app or web:** "My enquiries" screen/page shows the current status and any admin note, refreshed automatically each time it's opened.

## 6. Inventory sync, explained

- Every menu item has a `stockQty`.
- When a customer places an order, the backend runs the stock deduction and order creation **as a single atomic transaction** — if any item doesn't have enough stock, the entire order fails and nothing is deducted (no partial orders, no oversold items).
- If staff/admin cancels an order afterward, the stock is automatically restored.
- Staff can also manually adjust stock (restock, wastage, correction) from the Inventory page — every adjustment is logged with who made it and why, viewable via `GET /api/inventory/:menuItemId/logs`.

## 7. What's MVP-complete vs. what to build next for production

**Fully working now:**
- Auth (JWT, role-based) across all three apps
- Menu browsing, cart, checkout, order placement
- Order status tracking (customer) and status updates (staff/admin)
- Stock deduction/restoration tied to orders
- Venue enquiry submit → approve/reject workflow
- Manual inventory adjustments with audit trail
- Admin dashboard overview stats

**Not yet built — recommended next steps toward a CraftMyPlate-level production app:**

| Feature | Why it matters | Suggested approach |
|---|---|---|
| Push notifications | Customers/staff aren't notified of status changes in real time | Firebase Cloud Messaging; trigger from `updateOrderStatus` |
| Image upload | `imageUrl` is currently a plain text field | Add S3/Cloudinary upload endpoint, wire into admin's menu form |
| Real-time order updates | Dashboard currently requires manual refresh | Add Socket.IO or Server-Sent Events on the backend |
| Delivery address autocomplete / maps | Text-only address field right now | Google Places Autocomplete API in checkout |
| Staff/admin user management UI | Currently API-only (curl/Postman) | Build a `/users` page in the admin dashboard using the existing `api.listUsers`/`createUser` pattern |
| Order rating/reviews | Not present | New `Review` model tied to `Order` |
| Multi-address book, saved cards | Not present | Extend `User` model |
| Rate limiting, input sanitization hardening | Basic validation exists; production needs more | `express-rate-limit`, stricter `express-validator` chains on every route |
| Automated tests | None yet | Jest + Supertest for backend; RN Testing Library for the app |
| CI/CD, environment separation (staging/prod) | Not set up | GitHub Actions + separate `.env` per environment |

None of these require re-architecting what's here — the data model and API already have the right shape (e.g. `Order.paymentStatus` slots in cleanly; `Socket.IO` just adds a broadcast to the existing `updateOrderStatus` controller). This MVP is meant to be built on, not thrown away.

## 7.5. Extended features (coupons, chat, combos, banners, notifications, checkout extras)

These were added after the initial MVP. All are fully wired end-to-end (backend + admin +
customer web + mobile) except where noted:

- **Coupons**: Admin → **Coupons** to create percent/flat discount codes with optional minimum
  order, usage cap, and expiry. Customers apply them at checkout with live validation before
  placing the order.
- **Chat**: A real human support conversation between each customer and your admin/staff — not
  an AI bot. Customers see a floating chat button (web) or a Chat tab (app); admin sees all
  threads with unread counts under **Chat**. Polling-based (checks every few seconds), not
  instant push — upgrading to WebSockets for true real-time delivery is a reasonable next step
  if this becomes high-traffic.
- **Combo menus**: check "Combo" on a menu item (`isCombo`), then define option groups (e.g.
  "Choose your main") via `POST /api/menu/:id/combo-groups` — there's no dedicated admin UI page
  for this yet, so use a REST client for now. Customers see a "Customize" picker instead of a
  plain "Add" button on combo items.
- **Banners**: Admin → **Banners** to upload images or short videos (≤25MB) for the rotating
  carousel shown at the top of the customer app and website. Reorder with the ↑/↓ buttons, toggle
  live/hidden per banner.
- **Checkout extras**: event date, guest count, and geo-location (via the device/browser's
  built-in location — no API key needed) are now optional fields at checkout, useful for
  catering-style bookings.
- **Notifications**: Admin → **Notifications** to broadcast an announcement (e.g. "20% off this
  weekend!") to every customer's in-app feed. **This is in-app only** — it shows up when a
  customer opens the app/site, not as a phone push while the app is closed. True push requires
  setting up Firebase Cloud Messaging with your own Firebase project (device tokens, native
  config, a server-side send step) — that's a meaningful follow-up project, not a config toggle.
- **OTP login**: works fully in development — `POST /api/auth/otp/request` returns the code
  directly in the response (`devCode`) so you can test without an SMS provider. **In
  production** (`NODE_ENV=production`), that convenience is disabled for security, which means
  OTP login will silently stop working end-to-end until you wire in a real SMS provider (MSG91,
  Twilio, etc.) — the integration point is clearly marked in
  `backend/src/controllers/otp.controller.js`. Don't deploy with `NODE_ENV=production` until
  that's done, or OTP login will appear broken to real users with no visible error.
- **Razorpay**: needs your own Razorpay account and API keys (`RAZORPAY_KEY_ID`,
  `RAZORPAY_KEY_SECRET` in `backend/.env`) — test-mode keys are free and instant to generate from
  the Razorpay dashboard. Cash on Delivery works with zero external setup.
- **Multi-brand settlements**: commission and payout math is fully automatic based on each
  brand's `commissionPercent` and their menu items' sales — but actually paying a brand partner
  (bank transfer, etc.) happens outside this system; "Mark as paid" just records that it happened.
- **Google Maps**: only "use my current location" (lat/lng capture) is wired in, using the
  browser's/device's native geolocation — free, no key required. A full interactive map picker
  with address autocomplete needs your own Google Maps API key wired into the checkout screens;
  ask if you'd like that built once you have a key.
